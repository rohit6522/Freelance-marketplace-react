1. Introduction

The introduction to this Software Requirements Specification (SRS) provides an overview of the complete GigCraft web application. While reviewing this document, software engineers, project evaluators, and peer reviewers will find all architectural specifications, operational constraints, and technical definitions necessary to design, implement, and verify the software product described herein.

1.1 Purpose

The purpose of this SRS is to formally specify the technical architecture, behavioral characteristics, functional capabilities, and design constraints of GigCraft for academic assessment in Course 252 (INT) Continuous Assessment 3 (Autumn 2026). The intended audience includes software engineering instructors, project evaluators, academic peers, and full-stack developers reviewing or extending the platform.

1.2 Scope

(1) Software Product Name: GigCraft (Freelance Gig Marketplace).

(2) What the Software Will Do:

  • Provide an India-focused technical service marketplace connecting clients and top-tier freelancers.
  • Allow freelancers to publish multi-tier service gigs (Basic, Standard, Premium) priced in Indian Rupees (₹ INR).
  • Execute a deterministic order lifecycle governed by simulated escrow contracts that protect both buyer and seller.
  • Enable instant bi-directional messaging, typing indicators, and deliverable file sharing via WebSockets.
  • Provide 1-click Google OAuth authentication via Firebase alongside traditional email/password credentials with dynamic role selection (Client vs Freelancer).
  • Enforce localized Indian formatting (en-IN locale, Indian phone number validation, IST timestamps).

What the Software Will Not Do:

  • The software is an academic simulation and does not conduct live fiat banking transactions or collect credit card details.
  • It does not act as a legal arbitration authority or tax collection platform.

2. General Description

2.1 Product Perspective

GigCraft is an autonomous, self-contained, cloud-hosted web application operating on a modern client-server architecture. The frontend SPA communicates with the Express backend via REST endpoints and Socket.IO WebSocket streams. User data, gigs, orders, reviews, and escrow records persist in a cloud MongoDB Atlas replica set, with media hosted on Cloudinary and authentication federated through Firebase.

2.2 Product Functions

  • User Identity & Multi-Role Governance: Secure registration as Client, Freelancer, or Administrator with JWT HTTP-only cookie sessions and Firebase Google OAuth.
  • Gig Management: Freelancer authoring of three-tiered service packages, rich markdown descriptions, search tags, and thumbnail media.
  • Marketplace Discovery: Category-driven catalog exploration, keyword search, price range filtering in ₹ INR, and seller tier sorting.
  • Order Execution Pipeline: Deterministic state machine (pending → in_progress → delivered → completed or cancelled) with simulated escrow fund allocation.
  • Real-Time Collaboration: Socket.IO WebSocket messaging, active typing indicators, unread badges, and attachment sharing.
  • Reputation & Moderation: Verified post-order review submissions, mathematical recalculation of aggregate star ratings, and administrator moderation queues.

2.3 User Characteristics

  • Client (Buyer): Individuals, startups, or enterprise managers seeking digital services. Expected to have standard web literacy.
  • Freelancer (Seller): Technical professionals, designers, and developers offering services. They maintain a public portfolio, track earnings, and deliver completed assets.
  • Administrator: Platform maintainers managing user suspensions, reviewing reported content, and monitoring system telemetry.

2.4 General Constraints

  • Security Standards: Passwords must be hashed using bcrypt (12 rounds). Session cookies must enforce httpOnly, SameSite=lax, and secure in production.
  • Zero Commercial Liability: Payments are strictly simulated in an educational milestone escrow ledger; no real financial transactions take place.
  • Locale Constraints: Currency is locked to ₹ INR using Intl.NumberFormat('en-IN'); dates display in Asia/Kolkata (IST).
  • Platform Compatibility: Operates in all modern evergreen browsers (Chrome, Edge, Firefox, Safari) across mobile, tablet, and desktop viewports.

2.5 Assumptions and Dependencies

The application assumes client devices support modern ECMAScript standards and have WebSockets enabled. It depends on cloud infrastructure availability across Render, MongoDB Atlas, Cloudinary, and Firebase Identity Services.

3. Specific Requirements

3.1 External Interface Requirements

3.1.1 User Interfaces

The user interface follows a modern neo-brutalist editorial aesthetic with high contrast, sharp borders, deep emerald primary CTAs (#005d42), and 2px solid offset shadows (#0b1c30). Typography utilizes Space Grotesk for display headlines and Geist for body text, data tables, and input elements. All views adapt fluidly across mobile, tablet, and widescreen layouts.

3.1.2 Hardware Interfaces

Standard desktop, laptop, tablet, or smartphone hardware with active network connectivity. Minimum display resolution: 320px width.

3.1.3 Software Interfaces

Compatible with Node.js v20+, modern web browsers (Chrome, Edge, Firefox, Safari), MongoDB Atlas v6+, and the Firebase Web SDK v13.

3.1.4 Communications Interfaces

HTTPS (TLS 1.3) protocol for secure RESTful communication; WSS (WebSocket Secure) protocol with long-polling fallback for Socket.IO events.

3.2 Functional Requirements

3.2.1 Feature 1: User Authentication & Role-Based Access Control (with Google OAuth)

  • 3.2.1.1 Introduction: Provides dual-mode authentication via standard email/password or 1-click Google OAuth with dynamic role selection (Client vs. Freelancer).
  • 3.2.1.2 Inputs: User credentials (email, password, first/last name) OR Firebase Google ID token, email, display name, photo URL, and selected role.
  • 3.2.1.3 Processing: Validates payload; decodes and verifies Firebase token claims; checks MongoDB for existing account; hashes passwords via bcrypt (cost 12); sets signed JWT in an httpOnly cookie.
  • 3.2.1.4 Outputs: Authenticated User JSON object, session cookie, and redirect to role-specific dashboard.
  • 3.2.1.5 Error Handling: Returns 409 for duplicate emails; 401 for invalid credentials; 400 for malformed tokens.

3.2.2 Feature 2: Indian Freelance Gig Catalog, Search & Tiered Pricing (₹ INR)

  • 3.2.2.1 Introduction: Allows exploration of technical services categorized across Indian market niches with multi-attribute filtering.
  • 3.2.2.2 Inputs: Search query, category ID, price bounds (₹ min/max), delivery turnaround, sorting criteria.
  • 3.2.2.3 Processing: MongoDB text indexes and pipeline aggregation execute filtering; prices formatted via en-IN locale.
  • 3.2.2.4 Outputs: Paginated JSON array of gig cards with seller tier badges and package previews.
  • 3.2.2.5 Error Handling: 404 for nonexistent categories; empty state UI with fallback reset filters when zero gigs match.

3.2.3 Feature 3: Deterministic Milestone Contracts & Simulated Escrow Lifecycle

  • 3.2.3.1 Introduction: Governs order creation, execution, deliverable submissions, and simulated escrow release through a formal state machine.
  • 3.2.3.2 Inputs: Selected package tier (Basic, Standard, Premium), project specifications text, deliverable files.
  • 3.2.3.3 Processing: Validates buyer role; locks package price in simulated escrow ledger; executes state transitions (pending → in_progress → delivered → completed); updates transaction state atomically.
  • 3.2.3.4 Outputs: Order record, milestone timeline entry, transaction status, and automated Socket.IO status event.
  • 3.2.3.5 Error Handling: Returns 409 Conflict if an illegal transition is attempted (e.g. attempting to deliver a cancelled order).

3.2.4 Feature 4: Real-Time Bi-Directional Client-Freelancer Messaging (Socket.IO)

  • 3.2.4.1 Introduction: Direct in-app messaging between client and freelancer for project coordination.
  • 3.2.4.2 Inputs: Recipient ID, message text, attachment metadata.
  • 3.2.4.3 Processing: Authenticates socket connection with session cookie; joins user to private room; persists message; emits new_message event.
  • 3.2.4.4 Outputs: Instant message delivery, typing indicators, and unread count badges.
  • 3.2.4.5 Error Handling: Automatic reconnect with exponential backoff; fallback to HTTP polling if WebSocket is blocked.

3.2.5 Feature 5: Review & Rating Ecosystem with Admin Moderation

  • 3.2.5.1 Introduction: Post-delivery peer review system with aggregate rating recalculation and admin moderation tools.
  • 3.2.5.2 Inputs: Order ID, rating (1-5 stars), review comment, moderation action.
  • 3.2.5.3 Processing: Verifies order completion; enforces single review per order; recalculates gig/seller averages; allows admin hide/restore.
  • 3.2.5.4 Outputs: Published review card and updated star badge.
  • 3.2.5.5 Error Handling: 403 Forbidden for incomplete orders or unauthorized callers.

3.5 Non-Functional Requirements

Requirement Specification & Measurable Target
3.5.1 Performance 95% of API read operations resolve in < 150 ms. Production JS bundle < 350 KB gzip.
3.5.2 Reliability All order state and escrow transitions execute in atomic MongoDB replica transactions to guarantee zero orphaned records.
3.5.3 Availability 99.5% operational target. Automated health check monitoring at /api/health.
3.5.4 Security Bcrypt (cost 12), httpOnly JWT cookies, Helmet CSP whitelisting Google/Firebase, and custom MongoDB operator sanitization.
3.5.5 Maintainability Strict separation into Controllers, Services, and Models. CI test pipeline verifying 105 client tests and 18 server tests.
3.5.6 Portability Runs seamlessly across Windows, Linux, and macOS environments without native binary lock-ins.

3.7 Design Constraints

Monolithic single-service deployment where Express serves pre-built React static files on a single unified origin to guarantee third-party cookie compatibility across all web browsers.

3.9 Other Requirements

Comprehensive terms of service, privacy policy, community guidelines, and self-service account deletion conforming to modern web privacy practices.

7. Appendices

Appendix A: UI Walkthrough & Verification Evidence

  • Marketplace Discovery (/explore): Dynamic multi-attribute filtering by category, price slider in ₹ INR, seller rating, and delivery speed.
  • Authentication Modal (/login & /register): 1-click Firebase Google OAuth with interactive archetype selector (Client vs Freelancer).
  • Order Management Workspace (/orders): Visual timeline tracker showing current order state, active countdown timer, revision requests, and deliverable downloads.
  • Seller Analytics Dashboard (/dashboard): Real metrics indicating completed orders, positive review percentages, and 6-month simulated earnings in Indian currency (₹).

Appendix B: Database Schemas (Mongoose ODM Models)

The persistence layer utilizes 12 strongly typed Mongoose schemas:

  • User: Personal data, hashed password, googleId, role (client, freelancer, admin), avatar, active status.
  • FreelancerProfile: Professional headline, bio, Indian location (e.g. Bengaluru, Karnataka), skills, languages, work experience.
  • Gig: Service title, slug, category, three package tiers (Basic, Standard, Premium in ₹ INR), images, rating aggregates.
  • Order: Client ref, freelancer ref, package tier, price in ₹, milestone requirements, deliverable URLs, order status machine.
  • Payment: Simulated escrow transaction reference, status (held, released, refunded), timestamp.
  • Review: Order ref, gig ref, rating (1-5 stars), feedback text, seller response.
  • Conversation & Message: Chat threads, participants, message body, file attachments, read receipts.
  • Category: Canonical service taxonomy (Web Development, UI/UX, AI/ML, Video Animation, etc.).
